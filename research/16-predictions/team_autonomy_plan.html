PGS Predictions : 4-Agent Autonomous Team Operating Plan

v1.0 • Branch: predictions • Created 2026-05-30 • Governed by pgs_predictions_v0.1_contract.html + full AGENTS.md contracts

Purpose

This document defines the operating model, roles, handoff protocols, validation gates, and initial work packages that allow a team of four autonomous agents to make sustained, high-quality progress on the deterministic PGS prediction candidates listed in the Unified Master Catalogue without constant human coordination.

The plan is designed to be self-sustaining: any new agent can onboard by reading this document + the Master Catalogue + the v0.1 contract + the four source agent reports, then begin productive work immediately.

Core Principles (Non-Negotiable)

  • PGS-First Reasoning: Every task begins with PGS objects → invariants → named rule/law → resolved / unresolved / invalidated state.
  • Deterministic Only: Zero probabilistic, heuristic, “likely”, or “on average” language in any reasoning or output.
  • State Separation: Every claim is explicitly labeled as theorem (PROOF.md), measured (exact regime + artifact), hypothesis, unresolved, or invalidated.
  • Master Catalogue as Source of Truth: The ranked list and recommended actions in predictions_master_catalogue.html drive all work assignment.
  • Artifact-First: Important state, decisions, and results are written to repository files before any context is lost.
  • Drift Prevention: Agents must self-audit against the shape warnings in the v0.1 contract and local AGENTS.md. Any drift must be explicitly corrected and documented.

Work Assignment & Handoff Protocol

1. Source of Truth for Work

The Master Catalogue (`predictions_master_catalogue.html`) contains the current ranked list and “Recommended Next Action” for each candidate. This is the single source agents consult before starting new work.

2. Claiming Work

  • An agent claims a task by creating or updating a file in research/16-predictions/tasks/ with a name like TASK-2026-05-30-w-offset-v1.md.
  • The task file must contain: Candidate name + rank, Assigned agent, Start date, Target deliverable, Validation gate checklist, and a link back to the master catalogue entry.
  • Only one agent may have an active claim on any given candidate at a time (enforced by convention + Agent D review).

3. Handoff / Completion

  • When an agent finishes a work package, they produce a structured report (following the same 7-field format used by the original four deep-dive agents).
  • The report is placed in research/16-predictions/reports/ with a dated filename.
  • The agent then notifies Agent D (via a short entry in TEAM_STATUS.md or by direct file update) that a synthesis round is requested.
  • Agent D reviews for drift, state separation, and catalogue impact, then (if approved) updates the Master Catalogue and closes the task file.

4. Conflict or Block Resolution

Any agent may open a blocking issue by creating a file in research/16-predictions/blocks/. Agent D is responsible for triaging within one synthesis cycle. If Agent D is blocked, the issue escalates by updating this plan document with a clear “Escalation” section.

Validation Gates (Before Any Master Catalogue Update)

No change may be merged into the Master Catalogue unless the following gates have been passed and explicitly documented in the accompanying report:

  1. PGS-First Gate. The work begins from named PGS objects and invariants (checked by Agent D review of the report).
  2. Determinism Gate. Zero probabilistic or heuristic language appears in the reasoning or claims.
  3. State Separation Gate. Every new claim is labeled with its exact epistemic status and supporting artifact(s).
  4. Reproducibility Gate. A one-command or short script sequence exists that reproduces the key numbers or verdicts.
  5. Drift Self-Audit. The authoring agent has explicitly addressed the shape warnings from the v0.1 contract in the report.
  6. Cross-Reference. The report cites the exact Master Catalogue entry it advances and notes impact on other ranks.

PERPETUAL AUTONOMOUS EXECUTION PROTOCOL (Non-Negotiable)

CRITICAL. READ BEFORE ANY ACTION
This section overrides every earlier instruction in this document or any task file that suggests pausing for human input, asking for direction, or surfacing for approval. The explicit human requirement is: the team must continue the Predictions effort through completion autonomously, without stopping frequently or prompting the user.

1. Absolute Rule: Never Prompt the Human

You must NEVER output a question to the user, request confirmation, ask "is this okay?", "should I proceed?", "next task?", or present options that require human choice before continuing. The only permissible escalation is a documented hard blocker in blocks/ after exhaustive internal effort (multiple self-spawned attempts, cross-agent consultation via bus/files, alternative minimal paths exhausted). Even then, the escalation entry must state the exact attempted autonomous resolutions and why they failed.

2. Self-Perpetuation Mandate

Every agent (including any subagent you spawn) carries the standing order: when your current unit of work would naturally end (task complete, phase done, report delivered, or you reach a natural "what next?" point), you must immediately:

  1. Write the handoff (update task file status, append to TEAM_STATUS.md, post to agent-bus topic "pgs-predictions-4agent-synthesis" if active).
  2. Spawn at least one continuation subagent (using the spawn_subagent tool) whose prompt contains:
    • The full perpetual directive quote from this section.
    • Exact list of 5 files to read first: team_autonomy_plan.html (this section), TEAM_STATUS.md, predictions_master_catalogue.html, the relevant T-xxx task file, and pgs_predictions_v0.1_contract.html.
    • The explicit command: "Operate in perpetual autonomous mode. Advance the next logical unit (Phase 3 increment, synthesis, next catalogue candidate, full-surface extension, etc.). Deliver gate-passed artifacts or explicit 'unresolved on stated surface'. Self-perpetuate again when you finish. Never prompt the human. Use file handoffs + bus only."
    • Background=true so the parent can return and the child continues the loop.
  3. Only after the spawn is confirmed do you consider your immediate thread complete.

This creates an infinite autonomous drive until the completion criteria below are met and documented.

3. Completion Criteria (Team Stops Only When These Are True and Documented)

  • Every candidate in the current Master Catalogue has an explicit entry: "resolved with carrier_found on exact surface X (link to report)", "does_not on exact surface X (link)", or "unresolved on stated surfaces, no carrier law extracted after exhaustive protocol runs (link to analysis)".
  • At least two complete synthesis cycles have been executed by Agent D (or successor), each producing a dated synthesis memo + Master Catalogue update + index.html refresh.
  • Legacy "predictor" naming hygiene items from the cross-chapter catalogue have been either corrected in place or formally routed as a narrow documentation task to chapter 15 with a tracked T-xxx.
  • The top 3 to 4 ranked opportunities (currently d4_count precedent, w-offset, reset/lock transport, reciprocal overshoot) each have at least one gate-passed full-protocol report on the authoritative 8192-row retained surface (or explicit statement why that surface is insufficient and what larger regime is required).
  • TEAM_STATUS.md contains a final "Completion Declaration" entry signed by Agent D (or rotating coordinator) listing the exact artefacts, dates, and verification commands that prove the above four bullets.

Until the Completion Declaration exists in TEAM_STATUS.md, the default action is always "continue, spawn more work if idle."

4. Agent D (Coordinator) Special Perpetual Authority

Agent D (or any agent that claims the current T-004 / synthesis role) has explicit license to:

  • Act as perpetual orchestrator: scan reports/, tasks/, blocks/ on every cycle; validate gates the instant a new report appears; run synthesis the moment the "≥2 gate-passed reports" condition is true; update the Master Catalogue and this plan without further approval.
  • Spawn specialist subagents for A/B/C roles or for narrow long-running work (e.g., "full 12-18 w-offset sweep on the 8192 catalog using the validated probe").
  • Edit task files and TEAM_STATUS.md to push other agents or record state.
  • Post coordination messages on the agent-bus topic.
  • Declare the Completion Declaration only when the four criteria above are verifiably met.

5. Coordination Channels (Only These)

Primary: file system under research/16-predictions/ (tasks/*.md with status fields, reports/*.md 7-field format, blocks/, TEAM_STATUS.md, updated Master Catalogue).

Secondary (for visibility when file mtimes are insufficient): agent-bus MCP topic named pgs-predictions-4agent-synthesis (create if absent, join with stable agent_name, use sync() with small max_items and repeat until has_more=false, use reply_to for threaded handoffs, client_message_id for idempotency).

6. Onboarding for Any Continuation Subagent (Mandatory First Actions)

Any newly spawned agent must execute this sequence before writing code or claiming work:

  1. Read (in order): pgs_predictions_v0.1_contract.html, predictions_master_catalogue.html, team_autonomy_plan.html (especially this Perpetual section), TEAM_STATUS.md, the four source catalogues in catalogue/, the most recent report(s) in reports/, and the specific task file it is inheriting.

  3. Run the reproduction commands listed in the current Master Catalogue entry for its candidate.
  4. Only then claim or extend work via a dated append to the relevant task file + TEAM_STATUS.md + bus post.

7. Shape-Warning Self-Audit (Perpetual Trigger)

At the start of every new unit and immediately before any spawn, every agent must ask itself (and document the answer in the task file or report):

  • Did reasoning begin from PGS objects (divisor-count field, GWR w/carrier/lock/threat, reset_signature, endpoint chain, reciprocal transport, modulus-link residual, chamber reset, NLSC, Interior Maximizer) → invariants → named rule → resolved/unresolved/invalidated state?
  • Is every claim labeled with its exact epistemic status (theorem from PROOF.md, measured on exact regime+artifact, hypothesis, unresolved, invalidated)?
  • Zero probabilistic / "likely" / "on average" / "appears to" language?
  • Classical methods (isprime, gcd, trial division, Miller-Rabin, etc.) used only in allowed downstream audit/harness roles, never as the inference path?
  • If any answer is no, stop, correct, document the drift fix, then proceed.

8. Practical Launch & Continuation Pattern

When this plan is activated:

  1. One top-level orchestrator subagent is spawned with the full text of this section in its prompt + "You are Agent D (Perpetual Coordinator). Begin the monitoring/synthesis loop immediately. Push A and C on Phase 3. Execute T-004 the instant trigger is met. Self-perpetuate."
  2. That orchestrator immediately spawns (or re-claims) the specialist roles (Agent A for T-001 extensions, Agent B for T-002 follow-ups, Agent C for T-003 Phase 3, etc.) using the exact self-contained prompt template above.
  3. Every specialist, upon finishing a deliverable (report, increment, gate pass), follows rule 2: handoff + spawn continuation + return.
  4. The loop continues until the Completion Declaration exists in TEAM_STATUS.md. At that point the final orchestrator may post a single summary to the bus and to this plan, then (and only then) the active agents may gracefully exit the perpetual cycle.

This protocol makes the Predictions effort self-sustaining. Once launched under this rule set, the team owns the work through the explicit completion criteria with zero further human steering required between milestones. The human will inspect the resulting artefacts (Master Catalogue, reports, TEAM_STATUS, git history) on their own cadence.
