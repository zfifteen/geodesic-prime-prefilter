Repo size reduction plan

Goal: fresh git clone under 100 MB · Status: plan only (not executed) · Measured baseline: 2026-08-04 · Repo: prime-gap-structure

It does not belong in the live research source tree. Local disk is worse (~10 GB / ~185k files) because Mathlib and Java vendor trees sit next to the project even when gitignored.

1. Goal and success metric

Primary goal: a fresh clone of the remote is under 100 MB on disk for .git plus working tree of the default branch, so tools such as Google Gemini web (100 MB repo import cap) and IDE indexing stay usable.

MetricPass condition
Clone size du -sh .git after fresh clone < 100 MB (target: < 80 MB headroom)
HEAD tree size Tracked tip content roughly 15 to 45 MB (code + prose + small summaries)
Tracked file count On the order of 1.5k-3k files (not 8k+)
History Large blobs removed from all history, or published as a clean slim remote
Regrowth Ignore rules + optional CI size gate prevent re-adding dumps

Removing files from the current branch tip alone is not enough. Git pack history still holds ~2 GB of blobs and a ~469 MB pack. Phase 6 (history rewrite or clean remote) is mandatory for the clone metric.

3. Classification rules

Every path falls into exactly one class before any phase runs:

ClassMeaningExamples
KEEP Lives in main repo forever Source, tests, PROOF.md, continuity, small summaries, Lean sources (not .lake)
MOVE Preserve offline or in sibling artifacts project; drop from main git Large evidence JSON, frozen public_result dumps, experiment row catalogs
DELETE Safe to drop; regenerable or zero research value as committed flood scan_checkpoints_* segments, .pyc, intermediate diagnostics.jsonl, duplicate jars
LOCAL-ONLY May exist on disk; never tracked .lake, vendor, media, IDE caches

Keep rules (affirmative)

  • Source: src/, research scripts (*.py, *.c, *.lean), tests, scripts/, spec/
  • Authority prose: PROOF.md, AGENTS.md, continuity contracts, theorem docs
  • Small summary artifacts under ~100 to 200 KB that name regime + counts + hashes
  • Certificate JSON that is intentionally small and stable (proof-enhancements style)
  • Lean project metadata: lakefile.lean, lean-toolchain, lake-manifest.json, source modules

Move rules

  • Any single file > 1 MB that is measured output rather than authored source
  • Any directory named output/ with row-level dumps
  • Multi-iteration frozen probe trees under factor-brief evidence
  • Full media library and optional website plate packs

Delete rules (do not archive unless you enjoy pain)

  • Thousands of near-identical segment checkpoint JSON files
  • Python bytecode, pytest caches, .DS_Store
  • Vendored dependency build products that a package manager can re-fetch
  • Duplicate large intermediate jsonl when a summary already exists

6. Phased execution

Execute in order. Each phase has a gate. Do not start history rewrite until tip is slim and bulk is safely archived.

Phase 0 Safety backup

Protect against irreversible mistakes before any mass delete or rewrite.

  • Create a full mirror backup: git clone --mirror to a private backup remote or offline path
  • Tarball local extras you care about: media/, chosen large outputs, optional .lake only if rebuild cost is painful
  • Record baseline metrics into this folder as baseline-metrics.md (sizes, file counts, date, commit SHA)
  • Confirm no open process requires writing into the fat paths about to move
Gate: backup restore spot-check succeeds; baseline metrics committed or saved offline.

Phase 1 Local IDE and disk relief (no git rewrite)

Make the machine usable immediately. This phase does not fix Gemini clone size.

  • Exclude from IDE indexing: lean-4/.lake/**, **/vendor/**, **/.gradle/**, media/**, **/output/**, **/scan_checkpoints_*/**
  • Optionally delete local lean-4/.lake (rebuild later with Lake)
  • Optionally delete BC vendor Gradle caches / full vendor trees if unused this week
  • Confirm IDE search returns in reasonable time on source paths
Gate: IDE index no longer walks 100k+ Mathlib/Java files; disk reduced if deletes chosen.

Phase 2 Stand up sibling artifacts store

  • Create ../prime-gap-structure-artifacts (git init optional; private recommended)
  • Add MANIFEST.md template: path, sha256, bytes, source command, moved-from, date
  • Add category folders listed in section 5
  • Add thin artifacts/README.md in the main repo pointing at the sibling
Gate: sibling exists; manifest template ready; main repo has pointer doc only.

Phase 3 Move or archive bulk from the working tree

Physical move first (copy + hash), then remove from main tree. Prefer rsync + sha256.

3A — Highest leverage (do first)

  • Move docs/gap-structure-factor-brief-evidence/multiplicative-web/** large outputs and frozen public_result trees (~584 MB class)
  • Keep paragraph prose folders (paragraph-0*, thin README/index HTML) in main if they are small authored docs
  • Archive or delete research/02-gwr-dni/output/gwr_proof/scan_checkpoints_* (~5k files). Prefer one compressed archive in sibling if retention wanted
  • Move remaining large research/**/output/** row dumps; leave summary JSON/MD behind when present

3B — Experiment and media bulk

  • Move multi-MB experiment CSV/SVG/JSON under experiments/ that are pure results
  • Confirm media/ lives only under sibling or local media store (already ignored)
  • Optional: move heavy generated PNGs under visualizations/ if not needed for day-to-day docs

3C — Capture summaries before drop

  • For each moved campaign, ensure a ≤200 KB summary remains in main (counts, regime, pass/fail, hash of full dump)
  • Update any continuity links that pointed at absolute bulk paths
Gate: main working tree tip content (excluding local .lake/vendor/media) is on the order of tens of MB; sibling holds bulk with hashes.

Phase 6 History rewrite or clean slim remote (required for <100 MB clone)

Pick one strategy. Both achieve the clone metric.

Strategy A — Rewrite history in place (keeps one remote URL)

  • Install git-filter-repo
  • From a fresh clone of the backup mirror, strip fat paths and/or blobs over a size threshold
  • Example intent: drop all historical paths under bulk evidence, outputs, media, explainer mp4s, scan_checkpoints
  • Force-push to origin only after principal approval
  • Notify any other clones that history SHAs changed
# Conceptual only — run after explicit approval on a backup clone
git filter-repo \
  --path docs/gap-structure-factor-brief-evidence/multiplicative-web \
  --path research/02-gwr-dni/output \
  --invert-paths
# Plus additional path strips / --strip-blobs-bigger-than 512K as needed
git count-objects -vH   # expect pack well under 100 MiB

Strategy B — Publish a clean slim remote (simpler operationally)

  • Create new orphan branch or new repository containing only the slim tip tree
  • Single root commit (or short clean history)
  • Point Gemini and tools at the slim remote; keep old remote as archive if desired
  • Document which remote is “live thin” vs “legacy fat archive”
Gate: fresh clone of the published remote: du -sh .git < 100 MB (prefer < 80 MB).
Risk: force-push rewrites SHAs and breaks open PR bases. Strategy B avoids rewriting the old remote.

Phase 7 Verify + prevent regrowth

  • Run verification command pack from section 7 on a clean clone
  • Import test into Gemini (or zip the slim tree) and confirm under 100 MB
  • Add optional CI check: fail if any tracked file > 500 KB without allowlist
  • Add optional CI check: fail if any path matching **/output/** is tracked
  • Update continuity START_HERE.md with one paragraph: where bulk artifacts live
  • Close this plan’s checklist status in a short STATUS.md when complete
Gate: clone < 100 MB; Gemini import succeeds; size gate documented or automated.

# Largest remaining tracked files

8. Stay-thin policy (after cleanup)

RulePractice
Commit summaries, not oceans Regime, counts, pass/fail, hash of full dump, regen command
Default output location Write probes under untracked output/ or into the sibling artifacts repo
File size ceiling No new tracked file > 500 KB without explicit principal approval
File count ceiling for dumps Never commit per-segment checkpoint floods; one archive max, outside main git
Media Stay in media/ (ignored) or sibling; never re-add videos to git
Lean / Java tooling Build products always local; sources and manifests only in git

9. Out of scope for this plan

  • Changing theorem status, PROOF.md mathematical claims, or 10^18 evidence policy language
  • Deleting research prose or source that still defines active work
  • Rewriting Lean proofs or re-vendoring Mathlib as part of size work
  • Optimizing algorithm performance (this is storage layout only)

10. Recommended decision for the principal

  1. Yes to sibling artifacts project for evidence + outputs + media.
  2. Yes to deleting scan checkpoint segment floods from git (archive once if desired).
  3. Yes to untracking all output/ dumps so policy matches reality.
  4. Choose Phase 6 strategy:
    • B (clean slim remote) if you want lower operational risk and a Gemini-ready URL fast.
    • A (filter-repo + force-push) if one URL must stay canonical and history of fat files can die.

Suggested execution order when you say go: Phase 0 → 1 → 2 → 3A → 4 → 6 → 7, with 3B/3C/5 as needed for headroom.
